# VoltGuard MVP 产品设计文档（讨论稿）

> 状态：第一版已确认（2026-10-09）。仍待决定：热成像设备是否购买或借用（第 4 部分）、正式产品的传感器选型与覆盖范围。
> 最后更新：2026-10-09

## 1. 问题与机会

- 香港电动车数量快速增长（环保署：截至 2026 年 8 月约 184,000 辆，占登记车辆约 19.9%），大量车辆停放、充电在地下或室内停车场。
- 现行消防要求（消防处通函 4/2020，并于 5/2026 沿用）：设有充电设施、未装花灑的停车场须装热力或复合式火警探测器并连接火警系统；须设消防员紧急开关，可一次切断所有充电设施电源；每个喉轆位置加设干粉或二氧化碳灭火筒。
- 这些要求针对**起火后的探测与断电**，没有要求**起火前的早期异常发现**。锂电池热失控一旦开始便剧烈、持续且易复燃，越早发现越有处置时间。
- 机会：在现行消防系统之外，为停车场提供起火前的电池异常温度预警与处理指引，与法规要求互补而非替代。

来源：[消防处通函 4/2020](https://www.hkfsd.gov.hk/chi/source/circular/2020_04_chi_20200731_110104.pdf)、[消防处通函 5/2026](https://www.hkfsd.gov.hk/eng/source/circular/2026_05_eng_20260603_113355.pdf)、[环保署电动车数据](https://www.epd.gov.hk/epd/tc_chi/environmentinhk/air/promotion_ev/promotion_ev.html)。

## 2. 目标用户（已确认）

**付费客户与使用者：停车场物业 / 管理公司。**

| 角色 | 在 MVP 中做什么 |
|---|---|
| **控制室值班保安（主要角色）** | 收到告警 → 看热成像与 AI 说明 → 决定派人查看或报警。MVP 的界面与流程围绕此角色设计。 |
| 现场巡逻保安（次要） | MVP 中不单独设计，沿用现有前线简洁模式。 |
| 设施经理（次要） | MVP 中不单独设计，沿用现有事件记录与报告导出。 |

选择理由：告警后的最初几分钟由控制室决定是否升级处理，这是早期预警能否转化为行动的关键环节。

决定理由：
- 停车场可自行安装传感器，不依赖车厂或车主开放车辆电池数据（BMS），数据来源可行。
- 覆盖场内所有车辆，包括停放和充电中的车。
- 与「地下停车场电动车安全」的问题陈述一致。

未选方案：车队运营商（可取得 BMS 数据，但只覆盖自家车队，且车厂远程系统已有电池告警）；充电桩运营商（充电桩数据很少包含电池温度，且只覆盖充电中的车辆）。

## 3. 核心价值假设（已确认）

**更早发现 + 快速判断真假。**

> 假设：当热成像发现某辆车出现异常升温时，控制室值班保安借助 VoltGuard，能比依赖现有火警探测器**更早**知道，并能**更快、更准确**地判断是否需要派人查看或报警。

分工：
- **确定性规则负责「发现」**：根据热成像温度矩阵的最高温与升温速率触发告警，不依赖网络和 AI。
- **GenAI 负责「判断与解释」**：看热成像图，说明热点位于车辆哪个区域、更像电池异常还是刹车 / 排气 / 刚停车等常见热源，并给出值班保安能直接照做的下一步建议。

「更快」「更准确」的衡量方式见第 8 部分；「更早」需要真实异常数据，暂列为待验证。

## 4. 数据来源（已确认方向）

**场内热成像摄像头**：输出温度矩阵，接入现有矩阵导入与 2D/3D 温度图流程（现有系统支持 1–64 行/列）。

### 演示数据（已确认：先用仿真）

- MVP 先使用**明确标注为仿真**的热成像温度帧，演示完整流程（具体格式与场景见第 12 部分）。仿真帧不得进入实测记录与导出，也不得冒充实测数据；可以发送给 AI，保安决定存入单独的演示记录（见第 12 部分）。
- 无论使用什么设备，真实的电池热失控前兆都无法拍摄；真实设备只能提供正常热源（刚停的车、刹车、排气管），「异常」须用替代物或仿真表示，并在界面和演示中说明。

### 待决事项：是否购买或借用热成像设备

| 方案 | 大约费用 | 用途 | 难点 |
|---|---|---|---|
| MLX90640 模组（32×24） | 55–80 美元 | 现场实时演示（如对着暖包升温），矩阵直接符合现有导入格式 | 分辨率低；需接电脑或树莓派；到货时间 |
| 手机热成像镜头 InfiRay P2 Pro（256×192） | 239–279 美元 | 到停车场拍真车，为「判断真假」提供真实常见热源样本 | 较贵；须缩小到 64×64 以内；需停车场许可 |
| 向学校实验室借用 | 0 | 同上，取决于型号 | 能否借到、时间是否来得及 |

价格来源：[SparkFun](https://www.sparkfun.com/ir-array-sensor-55-degree-fov-mlx90640.html)、[Waveshare](https://www.waveshare.com/MLX90640-D110-Thermal-Camera.htm)、[InfiRay P2 Pro](https://xinfraredx.com/products/infiray-p2-pro-thermal-camera)（2026-10-09 查询）。

### 安装视角（已确认 2026-10-09）

摄像头装在**车道对面的墙或天花板边缘，离地约 2.5 米，向下约 30–45°**，正对车位拍摄停在车位里那辆车朝外的一端（通常是车头）。

- 看得到：车头正面、两个前轮、车底前缘及车下地面。
- 看不到：后轮、车尾、车辆两侧。车尾朝外停放时，看到的是车尾和后轮。
- 未选方案：两车位之间低角度侧拍（能看到整段车底，但相邻车辆容易遮挡，每个车位都要装）；天花板正上方俯拍（看不到车底和车轮，无法区分电池位置）。

待讨论：正式产品中的传感器选型与覆盖范围（充电车位 / 全部车位）。

## 5. GenAI 的作用

已确认方向：多模态模型看热成像图，区分电池区域异常与刹车、排气等常见热源，并生成给值班保安的下一步建议（见第 3 部分分工）。

### AI 的权限边界（已确认）

**AI 只提建议，值班保安确认后才生效，系统记录每次决定。**

- AI 判断热点更像常见热源时，给出「建议降级」；保安确认后告警才降级。
- 系统记录：谁、在什么时间、依据哪一次 AI 说明和哪一帧热成像，做了什么决定。
- AI 不可用或输出不合格时，只显示规则告警，并明确标示「AI 说明不可用」；不影响告警本身。

细则（已确认）：
- AI 也可以「建议升级」（例如热点位于电池底部），同样需要保安确认。
- 危险级别（最高温 ≥ 80°C 或升温 ≥ 2°C/s，均为原型阈值）不允许因 AI 建议而降级，只有警告级别可以。

未选方案：AI 只解释、不影响告警（最安全，但「判断真假」的价值有限）；AI 自动降级（AI 看错即漏报，责任无法交代）。

### AI 输出格式（已确认）

| 字段 | 由谁产生 | 内容 | 例子 |
|---|---|---|---|
| 热点位置 | **程序** | 按安装时预先划定的车位区域计算：车头 / 前轮 / 车底（电池位置）/ 其他位置；车尾朝外停放时显示为 车尾 / 后轮 | 前轮 |
| 可能成因 | AI | 固定选项之一：电池区域异常 / 刹车余热 / 刚停车余热 / 引擎或排气 / 阳光或环境 / 无法判断 | 刹车余热 |
| 建议 | AI | 升级 / 维持 / 降级 | 降级 |
| 理由 | AI | 一到两句，不含数字（数字由规则区单独显示） | 热点集中在轮毂位置且没有继续上升，更符合刹车余热 |
| 下一步 | AI | 固定动作，可多选：继续观察 / 派人查看 / 通知经理 / 拨打 999 | 继续观察 |
| 局限 | **程序** | 自动附上，例如仿真数据、低分辨率、未经实车验证 | 仿真数据 |

设计理由：
- 低分辨率热成像上车辆轮廓模糊，由 AI 猜测部位不可靠；预设区域让「位置」可重复、可测试，AI 只负责判断成因。
- 成因与下一步使用固定选项，便于统计与测试，也避免 AI 生成危险或无依据的操作。

程序对 AI 输出的一致性检查（不通过即视为「AI 说明不可用」）：
- 危险级别时，建议不得为「降级」。
- 成因为「电池区域异常」时，建议不得为「降级」。
- 「拨打 999」只能与「升级」同时出现。
- 字段与选项必须在上述固定范围内；理由不得含数字或安全保证、灭火、断电等操作性用语（沿用现有输出检查）。

## 6. MVP 功能范围（已确认）

| # | 功能 | 说明 | 现有代码复用 |
|---|---|---|---|
| 1 | 场内总览 | 按车位显示状态：正常 / 警告 / 危险 / 无数据 | 少，需新做 |
| 2 | 热成像帧接入 | 先读取标注清楚的仿真帧，接口预留给真实设备 | 多：矩阵导入、仿真按钮 |
| 3 | 规则告警 | 每个车位按最高温与升温速率判定 | 多：共享规则引擎 |
| 4 | 热成像查看 | 点开车位查看温度图 | 多：2D / 3D 温度图 |
| 5 | AI 看图说明 | 说明热点位置、像电池异常还是常见热源，给出升级 / 降级建议 | 中：AI 助手需改提示词与输出格式 |
| 6 | 保安确认 / 驳回并记录 | 确认或驳回 AI 建议，记录人、时间、依据 | 中：现有事件记录与处理流程 |
| 7 | 处置指引 | 派人查看、拨打 999 等下一步 | 多：前线模式、消防处官方指引 |

**现有 NASA 电芯功能**：移出主流程，保留为次要页面，用于说明「规则引擎已用真实电池数据验证过」。容量健康度等与热成像无关的功能不进入主流程。

## 7. 核心使用流程（已确认）

### 主流程：控制室值班保安

1. **平时**：控制室屏幕显示场内总览，所有车位正常。
2. **告警**：某车位热成像最高温超过警告阈值，车位变为琥珀色，屏幕出现告警条。
3. **查看**：保安点开车位，查看热成像图与规则结果（最高温、升温速率）。
4. **AI 说明**：数秒内显示 AI 说明，包括热点位于车辆哪个部位、更像电池异常还是常见热源、建议升级或降级及理由。
5. **决定**：保安确认或驳回 AI 建议，或直接派巡逻保安查看、拨打 999。
6. **记录与交接**：系统记录该决定；升至危险级别时显示处置指引，并可交由巡逻保安用手机前线模式跟进。

### 演示场景（均为标注清楚的仿真）

| 场景 | 热成像表现 | 规则结果 | AI 建议 | 保安操作 |
|---|---|---|---|---|
| A：常见热源 | 热点在前轮位置，温度稳定不再上升 | 警告 | 更像刹车余热，建议降级 | 确认降级，记录在案 |
| B：疑似电池异常 | 热点在车底（电池位置），持续升温 | 升至危险 | 建议升级 | 按指引拨打 999、通知经理 |

两个场景对比体现核心价值：同样触发告警，AI 帮助保安区分「不必紧张」与「必须立即行动」。

## 8. 成功指标（已确认）

### 用户测试

3 位参与者扮演值班保安，分别完成场景 A、B；每人分别使用「只有规则告警」与「规则 + AI 说明」两种界面，以对比「更快、更准确」。

| 指标 | 目标 |
|---|---|
| 从告警出现到做出决定的时间 | 有 AI 说明时 ≤ 60 秒，且快于只有规则时 |
| 决定正确（A 降级；B 升级或报警） | 有 AI 说明时至少 3 人中 2 人正确 |

### 技术指标

| 指标 | 目标 |
|---|---|
| 新热成像帧到达后规则告警更新 | ≤ 1 秒 |
| AI 说明返回 | ≤ 10 秒；超时或不合格时显示「AI 说明不可用」，告警不受影响 |
| 危险级别因 AI 建议被降级 | 0 次，由自动化测试保证 |

### 暂时无法衡量

「比现有火警探测器更早发现」需要真实的已标注异常事件数据，MVP 阶段列为待验证，不作为已达成的结论。

## 9. 不做什么（已确认）

- 不接入车辆电池管理系统（BMS）或车厂数据。
- 不控制充电桩、不自动断电：只提示，消防员紧急开关由人操作。
- 不预测起火概率，不替代法定火警系统。
- MVP 不接入真实摄像头：只预留接口，先用仿真帧。
- 不做多停车场管理、账号权限、收费。
- 不做气体或烟雾传感器。
- 不训练自有模型，使用现成的多模态模型。

## 10. 风险与待验证事项（已确认）

| 风险 | 说明 / 应对 |
|---|---|
| 无真实热成像数据 | 现有 NASA 数据是实验室单电芯记录，不能代表停车场中的整车；MVP 用标注清楚的仿真帧，硬件方案见第 4 部分待决事项 |
| 视角有盲区 | 每台摄像头只看到车辆朝外的一端，车尾、后半段车底和车侧的升温看不到或只能间接看到（见第 4 部分安装视角） |
| AI 看图能力未验证 | 低分辨率热成像（如 32×24）能否区分刹车与电池位置需实测 |
| 过度依赖 AI | 保安可能不看图直接确认；可考虑确认降级时须选择理由 |
| 隐私 | 热成像不能识别人脸，但仍属监控设备，须符合个人资料私隐专员公署要求（告示、保存期限） |
| OpenAI 地区可用性 | 香港调用可能受限，需准备替代方案 |
| 阈值未校准 | 60 / 80°C 与 1 / 2°C/s 为原型阈值，缺乏车型数据与专家背书 |

## 11. 车位总览界面（已确认）

控制室屏幕上常驻的主画面。

### 版面

```
┌──────────────────────────────┬──────────────────────┐
│  B2 层平面图（12 个车位）       │  告警队列             │
│  ┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐     │  按严重程度排序；      │
│  │充││充││充││充││充││充│     │  未处理的告警一直保留， │
│  └──┘└──┘└──┘└──┘└──┘└──┘     │  直到保安处理          │
│  ┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐     ├──────────────────────┤
│  │  ││  ││  ││  ││  ││  │     │  车位详情（点开后展开）  │
│  └──┘└──┘└──┘└──┘└──┘└──┘     │  热成像 · 规则结果 ·    │
│                              │  AI 说明 · 确认 / 驳回  │
└──────────────────────────────┴──────────────────────┘
```

- **左侧**：按停车场实际布局排列的车位平面图。
- **右侧上方**：告警队列，按严重程度排序；未处理的告警持续保留，直到保安处理。
- **右侧下方**：点开车位后在同一屏展开详情（热成像图、规则结果、AI 说明、确认 / 驳回按钮），保安不离开总览。

### 演示规模

1 层（B2）共 12 个车位：6 个充电位、6 个普通车位。

### 车位格子显示内容

- 车位号。
- 状态：正常 / 警告 / 危险 / 无数据；**颜色加文字或图标**，不只靠颜色区分。
- 最高温。
- 是否充电中。
- 超过 5 秒（原型参数）没有新热成像帧时显示「无数据」，不得显示为正常；刚接入、尚不足以判断时也显示「无数据」并注明「正在接入」。
- 正在告警的车位断线时，保留告警颜色并加「无数据」角标，告警不因断线而消失。
- 平时断线的车位不进告警队列，队列上方常驻一行「无数据车位」清单。

## 12. 演示场景仿真帧（已确认）

所有帧均为**仿真**，界面须标示「仿真演示」与「演示时间已压缩」；不进入实测记录与导出，不冒充实测数据。

仿真帧与 AI、决定记录（已确认 2026-10-09）：
- 仿真帧可以发送给 AI，AI 结果标示为「基于仿真帧」。
- 保安决定存入单独的演示记录，界面标示「仿真演示」，不可导出，按「重置」清空。

### 帧格式

- 每个车位 **32×24** 温度矩阵（与 MLX90640 模组一致，日后换成真实设备时格式不变；在现有 64×64 上限内）。
- 每秒 1 帧，压缩时间播放。
- 数值固定、不使用随机数，每次演示结果相同。
- 数值仅用于说明情况，**不是物理模型推算结果**。

### 两个场景

| | 场景 A：刹车余热 | 场景 B：疑似电池异常 |
|---|---|---|
| 背景与车身 | 地面约 28°C，车身 30–35°C | 同左 |
| 热点区域 | 前轮 | 车底（电池位置） |
| 温度变化 | 起始 68°C，每秒下降约 0.1°C | 38°C 缓升至 62°C（约 30 秒，约每秒 0.8°C），之后加速至每秒 2°C 以上，升至约 86°C |
| 规则结果 | 警告（温度 ≥ 60°C，无升温） | 先警告（温度 ≥ 60°C），后升为危险（≥ 80°C 且升温 ≥ 2°C/s） |
| 预期 AI 建议 | 成因：刹车余热；建议：降级；下一步：继续观察 | 成因：电池区域异常；建议：升级；下一步：拨打 999、通知经理 |
| 时长 | 约 60 秒 | 约 45 秒 |

### 其余 10 个车位

有车与空位混合，均为正常；其中 **1 个车位固定为「无数据」**，展示系统不会把数据中断当作正常。

### 演示控制

标示「仿真演示」的控制面板，三个按钮：**场景 A / 场景 B / 重置**，由负责操作演示的队员点击。
